# E3 check against the AI — 2026-10-15

SYSTEM_4 E3b (confidence, reason and page on what the AI reads) run against the real local model on the 4 sample
claims in `docs/imp/day1/samples` (complete 1–2, incomplete jd1–jd2): **before** = the prompts and schema just before
E3b (commit `c9c35d8`), **after** = E3b. Model `qwen/qwen3.6-35b-a3b` on the dev LM Studio. Read through the dev
preview (no cases created; the AI call log on dev records each call). Raw output kept outside the repo.

## Two bugs found and fixed by the check

1. **Any AI call over 5 minutes failed** ("fetch failed") — Node's `fetch` gives up after 300 s waiting for the response
   headers, whatever `LLM_TIMEOUT_MS` says. Affects UAT / production too. Fix: the AI call goes through `node:http`
   (`claim-recognition/llmClient.js`, `transport.post`); `LLM_TIMEOUT_MS` is the one timeout again.
2. **The model looped on the open `field_evidence` list** — the same entry repeated for 8 minutes / 22,088 tokens until
   the answer was cut mid-JSON. Fix: `field_evidence` is one fixed key per field (null when left null) — migration
   `20261015150000-field-evidence-by-field`, read back as the same list in code; the field-mapping answer capped at the
   6,000-token output reserve (`max_tokens`) — a cut-off answer → *Needs manual reading*, never retried; `vitamin_items`
   limited to 30.

- **Cost:** field mapping output ~1,100 → ~2,350 tokens; about **+25 s per claim**; largest answer 2,820 tokens — well
  inside the 6,000 cap and the context budget.
- **Page references: 100% valid** (60 / 60) — the review workspace's page links will work.
- **Doubt marks:** 1 in 42 pages. The reading step almost never marks doubt, including on Burmese names.
- **Confidence does not separate right from wrong on these samples.** Almost every value scored 0.95–1.0; values that
  are wrong scored high too:
  - complete-1: voucher date **2026-01-25** for a visit on 2026-07-25 (a 7 read as a 1, both versions) — scored 0.95.
  - complete-2: *Illness / injury* became a long English symptom list ("cough, cold, sore throat; fever; … dizziness")
    that is **not in the documents** — scored 0.8, reason "transcribed from medical record complaints section"
    (before: garbled Burmese — wrong too).
  - jd2: *Account holder* read as a different Burmese name in each run and on each form (the e-claim form read as
    "ကိုပေါင်ဆိုး", the notification form as "ကျော်ဇင်အောင်"; before "ကျော်သန်းဇော်") — scored 0.95.
- **Run-to-run variation dominates the differences:** the medical record's presence / legibility flipped between runs on
  2 of 4 samples (complete-1, jd1) — the same in both versions, at temperature 0.

## What it means

- E3 works end to end: structured evidence, valid pages, no loops, acceptable cost. Safe to deploy with the fixes.
- **The AI's self-scored confidence is not a reliable gate** with this model — it stays useful as an explanation
  ("typed on the claim form" vs "transcribed from the medical record"), not as the thing that catches misreads. The
  PRD already notes the scores are uncalibrated; E4-15 step 3 (thresholds from reviewer corrections, *✓ Right* data)
  is how they become meaningful.
- What did catch problems here were the **rules** (amount totals, cross-document dates) and would be **more rules**,
  each found in these samples (owner to decide):
  1. A voucher dated long before the visit (e.g. > 30 days) → unsure (complete-1).
  2. The same field read differently on the two forms (notification vs e-claim) → unsure (jd2 account holder) — needs
     the mapping to keep both readings.
  3. *Illness / injury* taken from the medical record instead of the claim form, or not found in any transcript →
     unsure (complete-2).
